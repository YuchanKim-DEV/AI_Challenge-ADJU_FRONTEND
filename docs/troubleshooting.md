## 1. 외부에서 WAS1의 80/443 접속 불가 (2026-09-01 해결)

### 증상
- 외부에서 `http://180.210.89.242/`, `https://180.210.89.242/` 접속 시 **20~25초 타임아웃**
- 같은 서버의 SSH(30022)는 **정상 접속**
- 서버 내부에서는 `curl http://localhost/` → **200 정상**

### 오진했던 것 (중요)
처음엔 **방화벽 인바운드 차단**으로 판단했다. 근거는:
- 신청서 수정본(8/29)에 80/443 규칙이 빠져 있었음
- 외부 접속이 전부 타임아웃

→ **틀렸다.** 방화벽은 처음부터 80/443을 통과시키고 있었다.
   하마터면 잘못된 개방 요청을 보낼 뻔했다.

또 하나의 오진: 한 번 `443 → Connection refused (25ms)`가 나온 것을 보고
"443은 방화벽 통과, 80만 차단"이라고 단정했으나, 재확인 시 443도 타임아웃이었다.
**단발 측정으로 결론 내리면 안 된다.**

### 진짜 원인 — 비대칭 라우팅 + 도커 DNAT

`tcpdump`로 패킷을 직접 캡처해서 확정했다.

```
eth1  In  IP 121.140.143.23.61425 > 10.200.40.77.80: Flags [SEW]   ← 요청 도착
eth0  Out IP 10.200.40.77.80 > 121.140.143.23.61425: Flags [S.E]   ← 응답이 다른 길로
```

**패킷은 서버에 도달했고 nginx도 정상 응답했다.** 문제는 응답 경로였다.

1. WAS1은 NIC가 2개다.
   - `eth0` = 10.10.10.240 (기본 경로, metric 100)
   - `eth1` = 10.200.40.77 (metric 200)
2. **공인 IP 180.210.89.242는 eth1(10.200.40.77)에 매핑**되어 있다.
   (신청서의 "WAS-1 사설 IP"는 10.10.10.240이 아니라 사실상 10.200.40.77 쪽)
3. 요청은 eth1로 들어오지만 응답은 기본 경로인 eth0으로 나가 중간 라우터가 폐기.
4. `ip rule`에 `200: from 10.200.40.77 lookup 2`가 이미 있었지만,
   **도커 DNAT를 거친 응답에는 적용되지 않는다.**
   라우팅 결정 시점에는 출발지가 컨테이너 IP(172.17.0.2)이기 때문.
   (SNAT로 10.200.40.77로 바뀌는 건 그 이후)
5. SSH는 도커를 거치지 않아 규칙 200에 걸리므로 계속 정상이었다.

### 해결

연결 단위로 표시(CONNMARK)를 남겨, eth1로 들어온 연결의 응답도 eth1로 나가게 한다.

```bash
# eth1로 들어온 새 연결에 mark 2 부여
sudo iptables -t mangle -A PREROUTING -i eth1 -m conntrack --ctstate NEW -j CONNMARK --set-mark 2
# 이후 패킷(컨테이너 응답 포함)에 mark 복원
sudo iptables -t mangle -A PREROUTING -j CONNMARK --restore-mark
# mark 2 트래픽은 table 2(eth1 경로) 사용
sudo ip rule add fwmark 2 lookup 2 priority 100
# ★ table 2에 도커 경로 추가 (이게 없으면 DNAT된 패킷이 컨테이너로 못 감)
sudo ip route add 172.17.0.0/16 dev docker0 table 2
```

**마지막 줄을 빠뜨리면 오히려 더 나빠진다.** 마킹만 적용하면 DNAT된 패킷이
table 2에서 172.17.0.0/16 경로를 못 찾아 컨테이너에 도달조차 못 한다.
(실제로 이 단계에서 SYN만 들어오고 응답이 아예 생성되지 않았다)

### 검증 결과
```
http  status=200 time=0.030
https status=200 time=0.060
api   status=200
```

### 영구화 (완료)
systemd 서비스 `adju-routing`으로 부팅 시 자동 적용된다.
스크립트 `/usr/local/bin/adju-routing.sh`, 유닛 `/etc/systemd/system/adju-routing.service`.
docker.service 이후 실행되도록 `Requires=docker.service`를 걸었다 (docker0이 있어야 하므로).

## 2. 포트 스캔이 방화벽에 차단되어 오진 유발 (2026-08-31 ~ 09-01)

### 증상
`nc`로 여러 포트를 연속 스캔하면 **모든 포트가 차단으로 나온다.**
심지어 실제로 열려 있고 SSH 접속이 되는 30022까지 "차단"으로 표시됐다.

### 원인
방화벽에 **포트 스캔 탐지**가 있어, 단시간에 여러 포트를 두드리면
해당 출발지 IP를 일시적으로 통째 차단한다.

### 영향
2026-08-31 저녁 "서버 3대 전체 접속 불가"로 판단한 것이 이 때문이었다.
실제로는 서버가 정상 가동 중이었고 컨테이너도 계속 돌고 있었다.

### 올바른 검증 방법
- **포트당 1회만**, 최소 15초 이상 간격을 두고 측정
- 스캔 도구(`nmap`, 연속 `nc` 루프) 사용 금지
- 가장 확실한 것은 **서버에서 `tcpdump`로 직접 캡처**하는 것

## 3. macOS가 `~/Downloads` 접근을 차단 (2026-08-31)

### 증상
```
ls: /Users/yuchan/Downloads: Operation not permitted
```
`sudo`로도 안 된다. 파일 권한 문제가 아니다.

### 원인
macOS TCC(개인정보 보호). `Downloads`·`Desktop`·`Documents`는
앱별로 별도 승인이 필요하다.

### 해결
- 파일을 `~/.ssh/`나 프로젝트 폴더로 **복사**해서 사용 (권장)
- 또는 시스템 설정 → 개인정보 보호 및 보안 → 전체 디스크 접근 권한에
  터미널/VS Code 추가 후 앱 재시작

pem 키도 이 문제로 `~/.ssh/`에 사본을 두고 사용 중이다.

## 4. 회사 DNS가 trycloudflare.com 차단 (2026-09-01)

### 증상
cloudflared 터널 주소가 회사망에서 `NXDOMAIN`으로 해석 실패.
구글 DNS(8.8.8.8)로는 정상 해석됨.

### 우회
```bash
curl --resolve <호스트>:443:<IP> https://<호스트>/
```
또는 기기 DNS를 8.8.8.8로 변경 / 모바일 데이터 사용.

※ 80/443 문제가 해결되어 터널은 더 이상 필요 없다.

## 5. `su - web` 인증 실패 (정상 동작)

`web` 계정은 `useradd`로만 만들어 **비밀번호가 없다**(`/etc/shadow`에 `!`).
서비스 전용 계정이라 의도된 설정이며, 원격 로그인이 불가능해 오히려 안전하다.

```bash
sudo -iu web              # 이렇게 전환
sudo -iu web docker ps    # 한 줄 실행
```
